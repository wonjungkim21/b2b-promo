
너는 최고의 비즈니스 도메인 전문가야. "b2b-promo"라는 이름의 식자재 유통 B2B 프로모션 웹 애플리케이션(교육용 바이브코딩 실습 MVP)을 만들려고 해. 다음 내용을 바탕으로 적절한 서브에이전트를 활용해 도메인 정의서 초안을 작성해줘.

## 문제 정의:

- 식자재를 구매하는 외식업체·급식업체 등 B2B 거래처가 진행 중인 프로모션 정보를 흩어진 채널(영업 담당자 개별안내, 전화, 카톡 등)로만 접해 놓치기 쉽다.
- 거래처 입장에서 어떤 프로모션이 진행 중인지 한눈에 확인하고 참여 의사를 남길 수단이 없다.
- 관리자 입장에서도 프로모션을 등록·관리하고 참여 반응을 확인할 창구가 없다.

## b2b-promo 앱의 주요 기능:

- 관리자는 프로모션(가격할인/사은품 증정/신제품 시식)을 등록·수정하고 게시/종료 상태를 관리함
- 프로모션에는 선택적으로 "게임 적용"(룰렛 뽑기 이벤트 등)을 붙일 수 있고, 이 경우 경품 목록을 등록함
- 거래처 담당자는 자가 회원가입 후 로그인하여 진행 중/예정 프로모션 목록과 상세를 조회함
- 거래처 담당자는 관심 있는 프로모션에 참여 신청할 수 있음 있음
- 게임 적용 프로모션은 참여 신청과 서버가 경품 목록 중 하나를 무작위로 즉시 추첨해 결과를 확정하고, 화면에는 룰렛 애니메이션 후 결과를 보여줌
- 거래처 담당자는 신청한 프로모션 목록(당첨 결과 포함)을 확인하고 필요 시 신청을 취소할 수 있음
- 관리자·거래처 담당자 공통으로 마이페이지(내 정보 조회/수정, 비밀번호 변경)를 제공함
- 모든 사용자는 인증(로그인) 후에만 애플리케이션 기능을 이용함
- 모바일(거래처 담당자가 현장에서 스마트폰으로 접속)과 데스크탑(관리자가 사무실에서 접속) 모두 대응하는 반응형 UI가 필요함

## 필수 사항:

- 도메인 정의서에는 핵심적인 내용만 포함하도록 함 (핵심 액터, 핵심 도메인 엔티티, 유스케이스, 예외케이스 및 비즈니스 규칙)
- MVP 범위(포함/제외)를 명시적으로 구분해서 정리함 — 특히 실제 주문/결제/정산, 재고 실시간 연동, 승인워크플로우, 거래처 등급별 차등가, 포인트 적립, 검색 기능, 경품 재고 관리는 이번 개발에서는 제외함
- "참여신청"은 (프로모션, 거래처) 조합당 유일해야 하고, 취소/재신청은 새 레코드가 아니라 기존 레코드의 상태 전환으로 처리한다는 규칙을 포함함
- 게임 적용 프로모션의 추첨은 재추첨은 허용하지 않음
- 작성된 도메인 정의서를 docs/ 디렉토리에 1-domain-definition.md 파일로 저장함

너는 최고의 비즈니스 도메인 전문가야.
"freshmeal-point-event"라는 이름의 **프레시밀 포인트 기반 이벤트 응모 웹 애플리케이션(교육용 바이브코딩 실습 MVP)**을 만들려고 해.
다음 내용을 바탕으로 적절한 서브에이전트를 활용해 도메인 정의서 초안을 작성해줘.

## 문제 정의:

* 프레시밀 사용자는 포인트를 보유하고 있어도 실제로 포인트를 사용할 수 있는 이벤트나 참여 기회가 적어 포인트 활용성이 낮다.
* 사용자가 현재 어떤 이벤트가 진행 중인지 한눈에 확인하고, 본인이 보유한 포인트로 참여할 수 있는 이벤트인지 쉽게 판단할 수 있는 기능이 부족하다.
* 사용자가 자신의 보유 포인트와 이를 통해 몇 회 응모할 수 있는지 직관적으로 확인하기 어렵다.
* 따라서 프레시밀에서 진행 중인 이벤트를 쉽게 인지하고, 보유 포인트를 응모 기회로 활용하여 이벤트에 직접 응모할 수 있는 기능이 필요하다.

## freshmeal-point-event 앱의 주요 기능:

* 사용자는 로그인 후 현재 진행 중이거나 예정된 이벤트 목록을 조회함
* 이벤트 목록 및 상세에서 이벤트명, 이미지, 이벤트 기간, 경품 또는 혜택, 이벤트 상태 등을 확인함
* 사용자는 자신의 현재 보유 포인트를 확인할 수 있음
* 이벤트 응모 기준은 MVP에서 **1,000포인트 = 응모 1회**로 고정함
* 시스템은 사용자의 보유 포인트를 기준으로 현재 최대 몇 회까지 응모할 수 있는지 계산하여 보여줌
* 사용자는 이벤트 상세에서 원하는 응모 횟수를 선택할 수 있음
* 응모 횟수 선택 시 사용 예정 포인트와 응모 후 예상 잔여 포인트를 즉시 보여줌
* 사용자가 응모를 확정하면 선택한 응모 횟수 × 1,000포인트를 차감하고 해당 이벤트의 응모를 완료함
* 예를 들어 5,500포인트를 보유한 사용자가 3회 응모하면 3,000포인트를 사용하고 잔여 포인트는 2,500포인트가 됨
* 사용자는 자신이 신청한 이벤트 목록과 각 이벤트별 응모 횟수, 사용 포인트, 응모 일시 등을 확인할 수 있음
* 관리자는 이벤트를 등록·수정하고 예정/진행중/종료 상태를 관리함
* 관리자는 이벤트별 전체 응모 횟수와 참여 사용자 수를 확인할 수 있음
* 모든 사용자는 인증(로그인) 후에만 애플리케이션 기능을 이용함
* 모바일에서 사용자가 쉽게 이벤트를 조회하고 응모할 수 있고, 데스크탑에서도 관리자가 사용할 수 있도록 반응형 UI로 구현함

## 필수 사항:

* 도메인 정의서에는 핵심적인 내용만 포함하도록 함
  (핵심 액터, 핵심 도메인 엔티티, 유스케이스, 예외케이스 및 비즈니스 규칙)
* 핵심 액터는 최소 **사용자, 관리자**로 구분함
* 핵심 도메인 엔티티는 최소 **User, Event, EventApplication, PointTransaction**을 포함함
* 이벤트 상태는 **예정 / 진행중 / 종료**로 구분하고, `진행중` 이벤트에 대해서만 응모할 수 있도록 함
* 포인트와 응모의 교환 기준은 MVP에서 **1,000포인트 = 응모 1회**로 고정함
* 보유 포인트가 응모에 필요한 포인트보다 부족한 경우 응모할 수 없음
* 사용자는 동일한 이벤트에 여러 번 응모할 수 있으며, 응모 횟수만큼 포인트를 사용함
* 동일 이벤트에 추가 응모하는 경우 새로운 사용자-이벤트 관계를 생성하기보다 기존 이벤트 참여 정보의 **누적 응모 횟수와 누적 사용 포인트를 증가시키는 방식**으로 관리함
* 각 포인트 차감 이력은 PointTransaction을 통해 별도로 추적할 수 있어야 함
* 별도의 응모권 Wallet은 만들지 않으며, **이벤트 응모 시 포인트를 즉시 응모 기회로 전환하여 사용하는 방식**으로 처리함
* 응모가 완료된 이후에는 사용자가 응모를 취소하거나 사용한 포인트를 반환받을 수 없음
* `포인트 차감`과 `이벤트 응모 등록`은 하나의 트랜잭션으로 처리하여 둘 중 하나만 성공하는 상황이 발생하지 않도록 함
* 사용자가 응모 버튼을 여러 번 누르거나 네트워크 재시도가 발생하더라도 동일한 응모 요청으로 포인트가 중복 차감되지 않도록 **멱등성**을 보장함
* 응모 처리 중 이벤트가 종료되거나, 포인트가 부족하거나, 잘못된 응모 횟수가 전달되는 경우 등의 예외케이스와 처리 규칙을 정의함
* MVP 범위(포함/제외)를 명시적으로 구분해서 정리함
* 도메인 정의서는 지나치게 복잡한 DDD나 엔터프라이즈 아키텍처 관점으로 작성하지 말고, 이후 화면 정의·API 정의·DB 설계로 바로 이어질 수 있도록 간결하고 명확하게 작성함
* 작성된 도메인 정의서를 `docs/` 디렉토리에 `2-domain-definition.md` 파일로 저장함

전문 서브에이전트를 이용해 다음 5가지 항목을 기준으로 방금 작성한 도메인 정의서를 평가해줘

- 완전성: 모든 핵심 영역 포함
- 명확성: 모호함 없는 명확한 정의
- 추적성: 요구사항과 구현 연결
- 검증 가능성: 테스트 가능한 기준
- 유지보수성: 지속적 업데이트 가능
