# 프레시밀 포인트 이벤트 응모(freshmeal-point-event) PRD

버전: v1.5 (2026-08-21, 상세 변경 이력은 12장 참조)
기반 문서: `docs/2-domain-definition.md` v1.6

## 1. 개요/배경

프레시밀 사용자가 보유 포인트로 진행 중 이벤트에 응모할 수 있는 웹 애플리케이션이다.

- 문제: 포인트를 소진할 이벤트/참여 창구가 없고, 진행 중 이벤트 및 응모 가능 여부·횟수를 직관적으로 파악하기 어렵다.
- 목표: 이벤트 조회, 보유 포인트 기반 응모 가능 횟수 계산, 포인트 차감을 통한 응모 기능을 제공한다.
- 응모 기준(고정값): 1,000포인트 = 응모 1회

본 문서는 바이브코딩 실습용 3일 1인 개발 MVP를 대상으로 하며, 이후 화면 정의서·API 정의서·DB 설계로 바로 이어지는 것을 전제로 한다.

## 2. 목표 및 성공 지표

- 비즈니스 목표
  - 가입자 1,000명 이상 확보 → 측정: User 테이블 row count (role=user)
  - 이벤트 응모 3,000회 이상 발생 → 측정: SUM(EventApplication.totalCount). 1,000포인트=1회 응모라는 정의상 이 값이 KPI의 "회"와 정확히 대응하는 단일 산식이다. PointTransaction 건수(type=EVENT_APPLY)는 "응모 요청 건수"를 나타내는 별도 참고 지표일 뿐 KPI 산식과 동일시하지 않는다(한 번의 응모 요청에서 여러 회를 선택하면 totalCount는 요청 횟수만큼 증가하지만 PointTransaction은 1건만 기록되어 두 값이 달라질 수 있음).
- 위 지표는 서비스 운영 이후 별도 관리자 대시보드/쿼리로 집계하며, MVP 개발 완료 자체의 산출물 판단 기준은 아니다(개발 완료 기준은 4~5장 기능 요구사항 충족 여부).

## 3. 대상 사용자

- 사용자(User): 자가 회원가입 후 로그인하여 이벤트를 조회·응모하는 일반 회원. 페르소나 상세 시나리오는 생략한다.
- 관리자(Admin): 이벤트를 등록·관리하고 응모 현황을 조회하는 운영자.
- 모든 기능은 로그인한 사용자만 이용 가능하다.

## 4. 범위

### 4.1 화면 단위 MVP 범위 (포함)
- 회원가입 화면
- 로그인 화면
- 이벤트 목록 화면 (사용자용, 진행중/예정만 노출)
- 이벤트 상세 화면 (응모 가능 횟수 확인, 응모 횟수 선택·미리보기·확정)
- 내 응모 내역 화면
- (UC-4 보유 포인트 조회는 별도 화면을 두지 않으며, 이벤트 목록/상세 등 사용자 화면 공통 영역에 노출한다. 정확한 배치는 화면 정의서에서 확정)
- 관리자 이벤트 목록/등록/수정 화면 (상태 변경 포함)
- 관리자 이벤트별 응모 현황 화면 (전체 응모 횟수, 참여 사용자 수)

### 4.2 제외 (Out of Scope)
11장 참조.

## 6. 비즈니스 규칙 요약

- 이벤트 status가 `진행중`일 때만 응모 가능. 응모 처리 시점에 종료로 바뀌었으면 차감 없이 거부 (5.1)
- 보유 포인트 < 응모 횟수×1,000 이면 차감 없이 거부. pointBalance는 항상 0 이상 (5.2)
- 응모 횟수는 1 이상 정수만 허용, 상한은 없고 포인트 부족 규칙으로 자연스럽게 제한 (5.3)
- 동일 User-Event 조합은 EventApplication 1건만 존재, 재응모 시 누적(totalCount/totalPointsUsed 증가) (5.4)
- 매 응모 성공 시 PointTransaction에 차감 이력 기록, 별도 Wallet 엔티티 없음 (5.5)
- 응모 완료 후 취소/환불 불가 (5.6)
- "포인트 차감 + PointTransaction 생성 + EventApplication 갱신"은 하나의 트랜잭션으로 원자적 처리 (5.7)
- 응모 요청은 멱등키를 동반하며, 동일 멱등키 재요청 시 재차감 없이 이전 결과 반환 (5.8)
- 동시 요청 처리 결과는 순차 처리와 동일해야 하며 pointBalance 음수 방지 (row lock 등으로 직렬화) (5.9)

## 7. 기술 스택 및 아키텍처 제약

- 프론트엔드: React 19, 전역 상태관리 Zustand, 서버 상태/통신 TanStack Query
- 백엔드: Node.js + Express, DB 드라이버는 pg 라이브러리 직접 사용 (ORM 미사용)
- 데이터베이스: PostgreSQL 17
- 인증 방식: JWT 기반, Access Token(짧은 만료, API 요청 인증) + Refresh Token(긴 만료, Access Token 재발급) 조합을 사용한다. 구체적인 만료 시간, 저장 위치(예: httpOnly 쿠키 등), 토큰 재발급/폐기 API 스펙은 API 정의서 단계에서 확정한다.
- 배포 인프라 등 그 외 사항은 본 PRD 범위 밖이며 이후 API/DB 설계 단계에서 결정한다.

## 8. UX/UI 요구사항

- 반응형 웹 UI 필수 적용 (모바일: 사용자 조회/응모, 데스크탑: 관리자 기능 포함). 별도 네이티브 앱은 만들지 않는다.
- 모바일 화면을 우선 고려하여 사용자 기능(목록/상세/응모/내역)을 설계하고, 관리자 기능은 데스크탑 사용을 기본 전제로 한다.
- 접근성(a11y)은 이번 프로젝트 범위에서 명시적으로 제외한다.
- 상세 와이어프레임/디자인 시스템은 본 PRD 범위 밖이며 화면 정의서에서 다룬다.

## 9. 일정 및 리소스

- 일정: 3일 이내 핵심 기능(4~5장 Must 항목) 완성
- 팀 구성: 1인 개발
- 예산: 별도 예산 없음 (1인 개발 규모)
- 위 제약으로 인해 범위는 4~5장에 정의된 최소 핵심 기능으로 한정하며, 테스트/디자인/QA에 별도 리소스를 할당하지 않는다.

## 10. 리스크 및 가정

- 3일/1인 제약으로 자동화 테스트는 최소 수준(핵심 트랜잭션 로직 위주)으로만 작성한다.
- 동시 요청 처리(5.9)는 DB row lock 등 단순한 방식으로 결과 기준만 충족시키며, 고도화된 분산 락/큐잉은 다루지 않는다.
- User.pointBalance 초기값은 회원가입 시 5,000을 지급하며, 그 외 포인트 충전/적립 로직은 만들지 않는다 (6장 제외 항목 참조).
- 이벤트 상태 전이는 관리자 수동 조작만 지원하며, 기간 기반 자동 전환 로직의 부재로 인한 운영 부담은 감수한다.
- 인증 방식은 JWT(Access + Refresh Token)로 확정했으나, Refresh Token 저장/폐기 방식에 따라 로그아웃 시 즉시 무효화가 어려울 수 있어(순수 JWT는 서버 측 세션 상태가 없음) API 설계 단계에서 Refresh Token 저장소(예: DB) 및 폐기 처리 방식을 함께 정해야 한다.

## 11. Out of Scope

도메인 정의서 6장 제외 범위에, PRD 자체 판단으로 추가한 UX 관련 제외 항목(접근성, 네이티브 앱)을 더한 목록이다.

- 응모 취소/환불 기능
- 포인트 충전, 적립, 만료 등 포인트 획득/소멸 관련 기능
- 당첨자 추첨, 발표, 경품 발송 등 이벤트 사후 처리 기능
- 응모권(Wallet) 등 포인트 외 별도 자원 엔티티
- 알림(이메일/푸시) 기능
- 다중 관리자 권한 세분화
- 이벤트 상태 자동 전환(스케줄러 기반), 결제/외부 연동
- 접근성(a11y) 대응
- 네이티브 모바일 앱
