# 프레시밀 포인트 이벤트 응모(freshmeal-point-event) 도메인 정의서

## 1. 개요/목적

프레시밀 사용자가 보유 포인트를 활용해 진행 중인 이벤트에 응모할 수 있도록 하는 교육용 바이브코딩 실습 MVP 웹 애플리케이션의 도메인을 정의한다.

- 문제: 포인트를 사용할 이벤트/참여 기회가 부족하고, 현재 진행 이벤트 및 응모 가능 여부·횟수를 직관적으로 파악하기 어렵다.
- 해결: 이벤트 목록/상세 조회, 보유 포인트 기반 응모 가능 횟수 계산, 포인트 차감을 통한 이벤트 응모 기능 제공.
- 응모 기준(MVP 고정값): **1,000포인트 = 응모 1회**

## 2. 핵심 액터

- **사용자(User)**: 자가 회원가입 후 로그인하여 이벤트를 조회하고 보유 포인트로 응모하는 일반 회원.
- **관리자(Admin)**: 이벤트를 등록·수정하고 상태(예정/진행중/종료)를 관리하며, 이벤트별 응모 현황을 조회하는 운영자.

모든 기능은 인증(로그인)된 사용자만 이용 가능하다.

## 3. 핵심 도메인 엔티티 및 관계

### 3.1 User (사용자)
- id
- name (표시 이름)
- loginId (로그인 식별자, 이메일 등)
- role (user / admin)
- pointBalance (현재 보유 포인트) — PointTransaction 이력의 합산으로 도출되는 파생값이 아니라 User에 별도 컬럼으로 저장·관리하며, 매 응모 시 PointTransaction 기록과 함께 동일 트랜잭션 내에서 갱신한다 (5.7 참조). 초기값 부여 방식(회원가입 시 지급 포인트, 시딩 데이터 등)은 포인트 충전/적립 기능과 함께 MVP 범위 밖이며, MVP에서는 이미 값이 채워진 상태로 가정한다(6장 참조). pointBalance는 항상 0 이상이어야 한다(5.2 참조).

### 3.2 Event (이벤트)
- id
- 이벤트명 — 필수
- 이미지 — 선택 (nullable)
- 이벤트 기간 (시작일시 ~ 종료일시, 종료일시는 시작일시보다 이후여야 함) — 필수
- 경품/혜택 설명 — 선택 (nullable)
- status: `예정` / `진행중` / `종료` — 필수
  - 상태 전이: 예정 → 진행중 → 종료. MVP에서는 관리자가 수동으로만 변경하며, 기간 기준 자동 전환은 지원하지 않는다(6장 제외 범위 참조).
  - **응모는 status가 `진행중`인 이벤트에 대해서만 가능하다.**

### 3.3 EventApplication (이벤트 응모)
- id
- userId (User 참조)
- eventId (Event 참조)
- totalCount (해당 이벤트에 대한 누적 응모 횟수)
- totalPointsUsed (해당 이벤트에 대한 누적 사용 포인트)
- lastAppliedAt (최근 응모 일시)
- 관계: **User-Event 조합당 EventApplication은 1건만 존재**한다. 동일 이벤트에 추가 응모 시 새 레코드를 만들지 않고 기존 레코드의 totalCount, totalPointsUsed를 누적 증가시킨다.

### 3.4 PointTransaction (포인트 거래 이력)
- id
- userId (User 참조)
- eventId / eventApplicationId (관련 응모 참조) — MVP 범위에서 type은 `EVENT_APPLY`만 존재하므로 실제로는 항상 non-null이다. nullable로 스키마를 열어두는 이유는 향후 다른 type(예: 관리자 수동 조정 등)이 추가될 때를 대비한 여유값이며, MVP 로직에서 이 필드가 null인 케이스는 발생하지 않는다.
- amount (항상 양수로 기록. 실제 증감 방향은 type으로 판단하며, MVP 범위에서는 `EVENT_APPLY`(차감) 한 종류만 존재하므로 모든 amount는 차감액을 의미한다)
- type (`EVENT_APPLY` 고정, MVP 범위에서는 차감만 존재)
- createdAt
- idempotencyKey (동일 요청 재시도 시 중복 차감 방지용 키, 유일값 제약)

### 3.5 관계 요약
- User 1 : N EventApplication
- Event 1 : N EventApplication
- User-Event 조합 1 : 1 EventApplication (누적 방식)
- EventApplication 1 : N PointTransaction (매 응모 시점마다 1건씩 이력 적재)

## 4. 유스케이스 목록

### 사용자
- UC-0. 회원가입한다. (관련 엔티티: User — name, loginId, role=user로 계정을 생성한다. pointBalance 초기값 부여 정책은 3.1/6장 참조로 MVP 범위 밖)
- UC-1. 로그인한다.
- UC-2. 진행 중/예정 이벤트 목록을 조회한다. (종료된 이벤트는 사용자 목록에서 제외한다. 단, UC-8 내 응모 내역에서는 종료된 이벤트도 조회 가능하다)
- UC-3. 이벤트 상세(이벤트명, 이미지, 기간, 경품/혜택, 상태)를 조회한다.
- UC-4. 본인의 보유 포인트를 조회한다.
- UC-5. 이벤트 상세에서 보유 포인트 기준 최대 응모 가능 횟수를 확인한다.
- UC-6. 응모 횟수를 선택하고 사용 예정 포인트·응모 후 예상 잔여 포인트를 미리 확인한다.
- UC-7. 응모를 확정하여 포인트를 차감하고 EventApplication을 갱신한다. (관련 규칙: 5.1, 5.2, 5.3, 5.7, 5.8, 5.9)
- UC-8. 본인이 신청한 이벤트 목록과 이벤트별 응모 횟수·사용 포인트·응모 일시를 조회한다.

### 관리자
- UC-9. 이벤트를 등록한다. (관련 규칙: 3.2 — 이벤트명/기간/status는 필수, 이미지/경품·혜택 설명은 선택이며, 종료일시는 시작일시보다 이후여야 한다)
- UC-10. 이벤트 정보를 수정한다. (관련 규칙: UC-9와 동일한 유효성 규칙 적용)
- UC-11. 이벤트 상태(예정/진행중/종료)를 변경한다. (관련 규칙: 3.2 상태 전이는 예정→진행중→종료 순서만 허용, 역방향 전이 불가)
- UC-12. 이벤트별 전체 응모 횟수와 참여 사용자 수를 조회한다.

## 5. 예외 케이스 및 비즈니스 규칙

### 5.1 상태 제약
- 이벤트 status가 `진행중`이 아니면(즉 `예정` 또는 `종료`) 응모할 수 없다.
- 응모 요청 처리 시점에 이벤트가 이미 `종료`로 바뀐 경우, 응모를 거부하고 사용자에게 종료되었음을 안내한다(포인트 차감 없음).

### 5.2 포인트 부족
- 보유 포인트가 (선택 응모 횟수 × 1,000) 미만이면 응모를 거부하고 포인트 부족을 안내한다(포인트 차감 없음).
- 불변식: 어떤 처리 결과로도 User.pointBalance는 음수가 될 수 없다. 이 불변식은 응모 처리(5.7 트랜잭션 내에서 차감 전 잔액을 재확인) 및 동시 요청 처리(5.9)를 통해 보장한다.

### 5.3 응모 횟수 유효성
- 응모 횟수는 1 이상의 정수여야 하며, 그 외 값(0 이하, 정수가 아닌 값, 숫자가 아닌 값)은 요청을 거부한다.
- 응모 횟수의 상한은 별도로 두지 않으며, 보유 포인트로 계산되는 최대 응모 가능 횟수(pointBalance ÷ 1,000의 정수부)를 초과하는 요청은 5.2 포인트 부족 규칙으로 거부한다.

### 5.4 누적 응모 방식
- 동일 이벤트에 여러 번 응모 가능하다.
- 응모할 때마다 필요한 만큼 포인트를 사용하며, User-Event 당 새 EventApplication 레코드를 만들지 않고 기존 레코드의 totalCount/totalPointsUsed를 누적시킨다.

### 5.5 포인트 이력 추적
- 매 응모 성공 시 PointTransaction에 차감 이력을 별도로 기록한다(차감액, 관련 이벤트/응모, 시각 포함).
- 별도의 응모권(Wallet) 엔티티는 두지 않는다. 이벤트 응모 시 보유 포인트를 즉시 응모 기회로 환산해 사용한다(포인트 잔액 = 응모 가능 자원의 단일 소스).

### 5.6 응모 취소/환불 불가
- 응모가 완료되면 취소하거나 사용한 포인트를 환불할 수 없다.

### 5.7 트랜잭션 원자성
- "User.pointBalance 차감", "PointTransaction 생성", "EventApplication 갱신(누적 응모 횟수/사용 포인트 증가)" 세 가지 변경은 하나의 트랜잭션으로 처리한다. 이 중 일부만 반영되는 부분 실패 상태가 존재해서는 안 된다.

### 5.8 멱등성
- 응모 요청은 멱등키(idempotency key)를 함께 전달받아 처리하며, PointTransaction.idempotencyKey는 유일값 제약을 가진다.
- 동일 멱등키로 재요청(중복 클릭, 네트워크 재시도 등)이 들어오면 포인트를 재차감하지 않고 이전 처리 결과를 그대로 반환한다.

### 5.9 동시 요청 처리
- 규칙(결과 기준): 동일 User-Event 조합에 대한 응모 요청이 동시에 여러 건(서로 다른 멱등키 포함) 들어오더라도, 모든 요청을 순서대로 하나씩 처리했을 때와 최종 결과(User.pointBalance, EventApplication.totalCount/totalPointsUsed)가 동일해야 하며, 어떤 경우에도 pointBalance가 음수가 되어서는 안 된다.
- 구현 예시: EventApplication 및 User.pointBalance 갱신을 DB row lock 등으로 직렬화하여 순차 처리하는 방식으로 위 결과 기준을 만족시킬 수 있다(구체적 구현 방식은 설계 단계에서 결정).
- 테스트 관점: 동일 User-Event에 N건의 동시 응모 요청(각 요청 횟수 c1..cN)을 보냈을 때, 잔액이 부족해지는 시점 이후의 요청은 모두 거부되어야 하고, 성공한 요청들의 (횟수×1,000) 합만큼만 최종 pointBalance가 감소해야 한다.

## 6. MVP 범위

### 포함
- 사용자 자가 회원가입
- 사용자 로그인(인증) 후 기능 이용
- 이벤트 목록/상세 조회 (이벤트명, 이미지, 기간, 경품/혜택, 상태)
- 보유 포인트 조회 및 응모 가능 횟수 계산(1,000포인트 = 1회 고정)
- 응모 횟수 선택 시 사용 예정 포인트/예상 잔여 포인트 미리보기
- 응모 확정 처리(포인트 차감 + EventApplication 누적 갱신, 원자적 처리, 멱등성 보장)
- 내 응모 내역 조회
- 관리자 이벤트 등록/수정 및 상태(예정/진행중/종료) 관리
- 관리자 이벤트별 전체 응모 횟수/참여 사용자 수 조회
- 반응형 UI(모바일: 사용자 조회/응모, 데스크탑: 관리자 기능 포함)

### 제외
- 응모 취소/환불 기능
- 포인트 충전, 적립, 만료 등 포인트 획득/소멸 관련 기능 (User.pointBalance는 회원가입 시 별도 시딩 데이터 등으로 이미 채워진 값으로 가정하며, 초기값 부여 절차 자체는 범위 밖)
- 당첨자 추첨, 발표, 경품 발송 등 이벤트 사후 처리 기능
- 응모권(Wallet) 등 포인트 외 별도 자원 엔티티
- 알림(이메일/푸시) 기능
- 다중 관리자 권한 세분화(역할 기반 세부 권한 관리)
- 이벤트 상태 자동 전환(스케줄러 기반), 결제/외부 연동
