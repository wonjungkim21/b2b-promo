# 프레시밀 포인트 이벤트 응모(freshmeal-point-event) 사용자 시나리오

버전: v1.1 (2026-08-13)
기반 문서: `docs/4-PRD.md` v1.4, `docs/2-domain-definition.md` v1.5

## 1. 개요

- 목적: PRD 5장 유스케이스(UC-0~UC-12)를 Given/When/Then 시나리오로 구체화하여, 이후 화면 정의서·API 정의서 작성의 입력 문서로 삼는다.
- 관계: 본 문서는 PRD와 도메인 정의서에 명시된 규칙을 그대로 인용하며, 새로운 규칙을 만들지 않는다. 각 시나리오에는 관련 도메인 정의서 5장 규칙 번호(예: 5.1, 5.2)를 표기한다.
- 형식: 모든 시나리오는 "Given(사전조건) / When(사용자 행동) / Then(시스템 반응 및 사후조건)" 형식으로 통일한다.

## 2. 액터 요약

- **사용자**: 자가 회원가입 후 로그인하여 이벤트를 조회하고 보유 포인트로 응모하는 일반 회원. 페르소나 상세 프로필은 PRD에서 의도적으로 생략했으므로 본 문서도 "사용자"라는 역할 수준으로만 다룬다.
- **관리자**: 이벤트를 등록·수정·상태 관리하고 응모 현황을 조회하는 운영자. 다중 관리자 권한 세분화는 범위 밖이며 단일 역할로만 다룬다.

## 3. 사용자 시나리오 (UC-0 ~ UC-8)

### 3.1 UC-0. 회원가입

**시나리오 3.1-1 (정상)**
- Given: 아직 계정이 없는 방문자가 회원가입 화면에 진입했다.
- When: name, loginId, 비밀번호 등 필수 정보를 입력하고 가입을 요청한다.
- Then: role=user로 User 계정이 생성되고, 로그인 화면으로 이동한다. (pointBalance 초기값 부여 방식은 범위 밖이며 시딩 데이터로 가정)

**시나리오 3.1-2 (예외: loginId 중복)**
- Given: 이미 존재하는 loginId를 입력했다.
- When: 가입을 요청한다.
- Then: 계정을 생성하지 않고 중복 오류를 안내한다.

### 3.2 UC-1. 로그인

**시나리오 3.2-1 (정상)**
- Given: 가입된 계정(loginId/비밀번호)을 보유하고 있다.
- When: 로그인 화면에서 인증 정보를 입력하고 로그인을 요청한다.
- Then: Access/Refresh Token이 발급되고, role에 따라 사용자 홈(이벤트 목록) 또는 관리자 화면으로 이동한다. (관리자도 동일한 로그인 기능을 사용한다)

**시나리오 3.2-2 (예외: 인증 실패)**
- Given: 잘못된 loginId 또는 비밀번호를 입력했다.
- When: 로그인을 요청한다.
- Then: 토큰을 발급하지 않고 인증 실패를 안내한다.

### 3.3 UC-2. 진행중/예정 이벤트 목록 조회

**시나리오 3.3-1 (정상)**
- Given: 로그인한 사용자가 이벤트 목록 화면에 진입했다.
- When: 목록 조회를 요청한다.
- Then: status가 `진행중` 또는 `예정`인 이벤트만 노출된다. `종료` 이벤트는 이 목록에서 제외된다(UC-8 내 응모 내역에서는 조회 가능).

### 3.4 UC-3. 이벤트 상세 조회

**시나리오 3.4-1 (정상)**
- Given: 사용자가 이벤트 목록에서 특정 이벤트를 선택했다.
- When: 이벤트 상세 조회를 요청한다.
- Then: 이벤트명, 이미지(있는 경우), 기간, 경품/혜택 설명(있는 경우), status가 표시된다.

### 3.5 UC-4. 보유 포인트 조회

**시나리오 3.5-1 (정상)**
- Given: 로그인한 사용자가 사용자 화면(목록/상세 등 공통 영역)에 있다.
- When: 화면이 로드된다.
- Then: 본인의 현재 pointBalance가 표시된다.

### 3.6 UC-5. 최대 응모 가능 횟수 확인

**시나리오 3.6-1 (정상)**
- Given: 사용자가 `진행중` 이벤트 상세 화면에 있고 보유 포인트가 있다.
- When: 화면이 로드된다.
- Then: 최대 응모 가능 횟수 = pointBalance ÷ 1,000의 정수부가 표시된다. (도메인 5.3)

**시나리오 3.6-2 (예외: 포인트 1,000 미만)**
- Given: 보유 포인트가 1,000 미만이다.
- When: 이벤트 상세 화면이 로드된다.
- Then: 최대 응모 가능 횟수가 0으로 표시되고, 응모 확정 진입이 비활성화된다.

### 3.7 UC-6. 응모 횟수 선택 및 미리보기

**시나리오 3.7-1 (정상)**
- Given: `진행중` 이벤트 상세 화면에서 응모 횟수 입력란이 있다.
- When: 사용자가 응모 횟수(1 이상 정수)를 입력/선택한다.
- Then: 사용 예정 포인트(횟수×1,000)와 응모 후 예상 잔여 포인트(pointBalance - 사용 예정 포인트)가 미리 표시된다.

**시나리오 3.7-2 (예외: 잘못된 응모 횟수 입력)**
- Given: 사용자가 0, 음수, 소수, 숫자가 아닌 값을 응모 횟수로 입력했다.
- When: 미리보기를 시도한다.
- Then: 유효성 오류를 안내하고 미리보기 값을 계산하지 않는다. (도메인 5.3)

### 3.8 UC-7. 응모 확정

**시나리오 3.8-1 (정상)**
- Given: `진행중` 이벤트이고, 보유 포인트 ≥ 선택 횟수×1,000이며, 유효한 멱등키를 포함한 응모 요청을 준비했다.
- When: 사용자가 응모 확정을 요청한다.
- Then: 하나의 트랜잭션으로 User.pointBalance 차감, PointTransaction(type=EVENT_APPLY, amount=횟수×1,000, idempotencyKey 포함) 생성, EventApplication의 totalCount/totalPointsUsed 누적 갱신이 원자적으로 처리되고, 갱신된 결과(잔여 포인트, 누적 응모 횟수)가 사용자에게 표시된다. (도메인 5.4, 5.5, 5.7)

**시나리오 3.8-2 (예외: 포인트 부족)**
- Given: 보유 포인트 < 선택 횟수×1,000이다.
- When: 응모 확정을 요청한다.
- Then: 포인트 차감 없이 요청을 거부하고 포인트 부족을 안내한다. (도메인 5.2)

**시나리오 3.8-3 (예외: 응모 처리 시점 이벤트 종료)**
- Given: 요청 시점에는 `진행중`이었으나, 서버에서 처리하는 순간 이벤트 status가 `종료`로 변경되었다.
- When: 응모 확정 요청이 처리된다.
- Then: 포인트 차감 없이 요청을 거부하고 이벤트가 종료되었음을 안내한다. (도메인 5.1)

**시나리오 3.8-4 (예외: 동일 이벤트 재응모 - 누적)**
- Given: 사용자가 동일 이벤트에 이미 1건의 EventApplication(totalCount=N)을 가지고 있다.
- When: 같은 이벤트에 추가로 응모를 확정한다(포인트 충분, 이벤트 진행중).
- Then: 새 EventApplication을 만들지 않고 기존 레코드의 totalCount/totalPointsUsed를 누적 증가시킨다. (도메인 5.4)

**시나리오 3.8-5 (예외: 멱등 재요청)**
- Given: 이전에 동일 idempotencyKey로 응모가 이미 성공 처리되었다.
- When: 네트워크 재시도 또는 중복 클릭으로 동일 idempotencyKey를 가진 요청이 다시 들어온다.
- Then: 포인트를 재차감하지 않고 이전 처리 결과를 그대로 반환한다. (도메인 5.8)

**시나리오 3.8-6 (예외: 응모 완료 후 취소 요청)**
- Given: 응모가 이미 완료되었다.
- When: 사용자가 취소/환불을 요청한다(해당 기능은 UI에 제공되지 않음).
- Then: 취소/환불 기능 자체가 존재하지 않으므로 처리되지 않는다. (도메인 5.6)

### 3.9 UC-8. 내 응모 내역 조회

**시나리오 3.9-1 (정상)**
- Given: 로그인한 사용자가 내 응모 내역 화면에 진입했다.
- When: 조회를 요청한다.
- Then: 본인이 응모한 이벤트 목록과 이벤트별 totalCount, totalPointsUsed, lastAppliedAt이 표시된다. 이벤트 status가 `종료`인 경우에도 목록에 포함된다.

## 4. 관리자 시나리오 (UC-9 ~ UC-12)

### 4.1 UC-9. 이벤트 등록

**시나리오 4.1-1 (정상)**
- Given: 관리자가 이벤트 등록 화면에서 이벤트명, 기간(시작~종료), status를 입력하고 이미지/경품·혜택 설명은 선택적으로 입력했다.
- When: 등록을 요청한다.
- Then: 이벤트가 생성되고 목록에 노출된다.

**시나리오 4.1-2 (예외: 필수값 누락 또는 기간 오류)**
- Given: 이벤트명/기간/status 중 하나가 누락되었거나, 종료일시가 시작일시보다 이르거나 같다.
- When: 등록을 요청한다.
- Then: 등록을 거부하고 유효성 오류를 안내한다. (도메인 3.2, UC-9 관련 규칙)

### 4.2 UC-10. 이벤트 정보 수정

**시나리오 4.2-1 (정상)**
- Given: 관리자가 기존 이벤트의 정보를 수정하려 한다.
- When: 이벤트명/이미지/기간/경품·혜택 설명을 변경하고 저장을 요청한다.
- Then: UC-9와 동일한 유효성 규칙(필수값, 기간 순서)을 통과한 경우에만 변경 내용이 저장된다.

**시나리오 4.2-2 (예외: 유효성 위반)**
- Given: 수정 내용이 UC-9의 유효성 규칙을 위반한다(예: 종료일시 < 시작일시).
- When: 저장을 요청한다.
- Then: 수정을 거부하고 오류를 안내한다.

### 4.3 UC-11. 이벤트 상태 변경

**시나리오 4.3-1 (정상)**
- Given: 이벤트 status가 `예정`이다.
- When: 관리자가 상태를 `진행중`으로 변경 요청한다.
- Then: status가 `진행중`으로 변경되고, 이후 사용자 응모가 가능해진다.

**시나리오 4.3-2 (정상)**
- Given: 이벤트 status가 `진행중`이다.
- When: 관리자가 상태를 `종료`로 변경 요청한다.
- Then: status가 `종료`로 변경되고, 이후 사용자 응모가 거부된다(3.8-3 참조).

**시나리오 4.3-3 (예외: 역방향 전이)**
- Given: 이벤트 status가 `진행중` 또는 `종료`이다.
- When: 관리자가 이전 단계(`진행중`→`예정`, `종료`→`진행중` 등)로 되돌리는 상태 변경을 요청한다.
- Then: 상태 변경을 거부한다. (도메인 3.2 상태 전이 규칙)

**시나리오 4.3-4 (예외: 단계 건너뛰기)**
- Given: 이벤트 status가 `예정`이다.
- When: 관리자가 `예정`→`종료`로 한 단계를 건너뛰는 상태 변경을 요청한다.
- Then: 상태 변경을 거부한다. (도메인 3.2 상태 전이 규칙)

### 4.4 UC-12. 이벤트별 응모 현황 조회

**시나리오 4.4-1 (정상)**
- Given: 관리자가 특정 이벤트의 응모 현황 화면에 진입했다.
- When: 조회를 요청한다.
- Then: 해당 이벤트의 전체 응모 횟수(SUM totalCount)와 참여 사용자 수(EventApplication row count)가 표시된다.

## 5. 예외/엣지케이스 시나리오 모음

아래는 3~4장에 등장한 예외 시나리오를 도메인 정의서 5장 규칙 번호 기준으로 재정리한 요약이다.

| 규칙 번호 | 예외 상황 | 처리 결과 | 관련 시나리오 |
|---|---|---|---|
| 5.1 | 응모 처리 시점에 이벤트가 `종료`로 전환됨 | 포인트 차감 없이 거부, 종료 안내 | 3.8-3 |
| 5.2 | 보유 포인트 < 선택 횟수×1,000 | 포인트 차감 없이 거부, 포인트 부족 안내. pointBalance는 항상 0 이상 | 3.8-2 |
| 5.3 | 응모 횟수가 1 이상 정수가 아님(0 이하/소수/비숫자) | 요청 거부, 유효성 오류 안내 | 3.7-2 |
| 5.4 | 동일 User-Event 재응모 | 새 레코드 생성 없이 기존 EventApplication 누적 갱신 | 3.8-4 |
| 5.5 | 매 응모 성공 | PointTransaction에 차감 이력 별도 기록(Wallet 엔티티 없음) | 3.8-1 |
| 5.6 | 응모 완료 후 취소/환불 시도 | 기능 자체 미제공, 처리 불가 | 3.8-6 |
| 5.7 | 응모 확정 처리 중 일부만 반영되는 부분 실패 상황 | 포인트 차감/PointTransaction 생성/EventApplication 갱신을 하나의 트랜잭션으로 원자적 처리, 부분 실패 없음 | 3.8-1 |
| 5.8 | 동일 멱등키로 중복 클릭/재시도 요청 | 재차감 없이 이전 처리 결과 그대로 반환 | 3.8-5 |
| 5.9 | 동일 User-Event에 대한 동시 다건 응모 요청 | 순차 처리와 동일한 최종 결과 보장(row lock 등으로 직렬화), pointBalance 음수 불가, 잔액 부족 시점 이후 요청은 모두 거부 | (3.8-1, 3.8-2와 결합하여 검증) |
